# OAuth・LocalStorage・データアクセス権限の解説

第二の脳アプリの OAuth 認証・データ保存・権限の仕組みを、Tackman さんが他ユーザーの Drive データを読めない理由まで含めて整理する。

---

## 1. OAuth とは

OAuth は「**アプリに、パスワードを渡さずに、ユーザーのデータへの限定的なアクセス権を与える仕組み**」。

### 例え話
ホテルのルームキーのようなもの：
- ホテルのフロント（Google）が、あなた（ユーザー）のカードキー（アクセストークン）を発行
- カードキーには「301号室だけ開ける」「24時間で無効」など、限定的な権限が組み込まれている
- ホテル全体のマスターキー（あなたの Google パスワード）は渡さない

### OAuth で出てくる3つの役者

```
┌─────────────────┐         ┌─────────────────┐
│  ユーザー       │         │  Google         │
│  （リソース     │ ◀────── │ （リソース      │
│   オーナー）    │  認可   │   サーバー）    │
└─────────────────┘         └─────────────────┘
        │                            ▲
        │  アクセストークン           │
        │  （限定的な権限）           │
        ▼                            │
┌─────────────────┐
│  アプリ         │
│ （second-brain）│
└─────────────────┘
```

1. **ユーザー**（あなた）：データの所有者
2. **Google**：データの保管場所（Drive、YouTube など）
3. **アプリ**（second-brain）：データにアクセスしたい第三者

### OAuth の認証フロー（簡略版）

```
[1] アプリが「ユーザーの Drive を使わせて」と Google に依頼
    ↓
[2] Google がユーザーに「second-brain に Drive へのアクセスを許可しますか？」と確認
    ↓
[3] ユーザーが「許可する」をクリック
    ↓
[4] Google がアプリに「アクセストークン」を発行
    ↓
[5] アプリはアクセストークンを使って Google Drive のファイルを読み書き
```

## 2. アクセストークン vs リフレッシュトークン

OAuth には2種類のトークンがある。

| トークン | 有効期限 | 用途 | 保存場所 |
|---|---|---|---|
| **アクセストークン** | **1時間程度**（短い） | API を呼ぶたびに提示する「入場券」 | メモリ上だけ（揮発性） |
| **リフレッシュトークン** | **半永久的**（長い） | アクセストークンを再発行するための「親札」 | **慎重に保管**が必要 |

### 例え話
- **アクセストークン** = 映画の 1 回券（1 時間で無効）
- **リフレッシュトークン** = 会員証（新しい 1 回券を発行してもらえる）

```
┌──────────────────────────────────────────┐
│  認証フロー                                │
│                                            │
│  [初回] ユーザーが「許可」                  │
│     ↓                                      │
│  Google がアクセストークン + リフレッシュ   │
│  トークンを発行                             │
│     ↓                                      │
│  アプリはアクセストークンで API 呼び出し     │
│     ↓                                      │
│  [1時間後] アクセストークンが無効化          │
│     ↓                                      │
│  アプリはリフレッシュトークンで              │
│  新しいアクセストークンを要求                │
│     ↓                                      │
│  Google が新しいアクセストークンを発行       │
│     ↓                                      │
│  以降、この繰り返し                        │
└──────────────────────────────────────────┘
```

### リフレッシュトークンが漏れると？
- **第三者が、永続的にあなたのデータにアクセスできる**
- アクセストークンの有効期限が切れても、リフレッシュトークンから新しいアクセストークンを発行できるから
- だから「**慎重に保管**」が必要

## 3. LocalStorage とは

ブラウザに備わっている **小さなデータ保存領域**（通常 5〜10 MB）。

### 特徴
- ブラウザ内に保存される（サーバーには送られない）
- **同じドメイン**で複数タブ・複数セッションをまたいで共有される
- ブラウザを変えると引き継がれない
- ユーザーが明示的に削除するまで残る

### 例え話
- ロッカーのようなもの
- 同じロッカー（同じブラウザ・同じドメイン）で何度も出し入れできる
- 鍵を変えると（別のブラウザで開く）中は見えない

---

## 4. 「ブラウザを変える」「タブを消す」「デバイス変更」の挙動

| シナリオ | リフレッシュトークンは残る？ | 蓄積したデータは残る？ | 必要な作業 |
|---|---|---|---|
| **タブを閉じる** | ✅ 残る | ✅ 残る | なし（次回開いた時にそのまま使える） |
| **ブラウザを再起動** | ✅ 残る | ✅ 残る | なし |
| **ブラウザを変える**（Edge → Chrome） | ❌ 消える | ⚠️ 残る（Drive に保存されていれば） | 新しいブラウザで再 OAuth 認証 |
| **PC を変える** | ❌ 消える | ✅ 残る（Drive に） | 新しい PC で再 OAuth 認証 |
| **スマホを変える** | ❌ 消える | ✅ 残る（Drive に） | 新しいスマホで再 OAuth 認証 |
| **「シークレットウィンドウ」を使う** | ❌ 消える | ✅ 残る（Drive に） | シークレットを閉じると消える |

### 重要なポイント
**リフレッシュトークンはブラウザ単位のデータ**だが、**蓄積した Knowledge / Task / Great Mind は Google Drive に保存されている**。だから：

```
ブラウザ A（Edge）  → リフレッシュトークン A で認証
                     → Drive に Knowledge を書き込み

ブラウザ B（Chrome）→ リフレッシュトークン B はない
                     → ユーザーは再 OAuth 認証が必要
                     → 同じ Google アカウントなので、同じ Drive にアクセスできる
                     → 過去に書き込んだ Knowledge が見える！
```

つまり、**デバイスやブラウザが変わっても、Google アカウントが同じなら、蓄積したデータは共有される**。リフレッシュトークンはデバイスごとに再発行が必要だが、データは Google Drive 上にあるので引き継がれる。

## 5. 設計案 B：リフレッシュトークンをブラウザ側に保存

CLAUDE.md で確定した方針：「各自の Google Drive に保存」を維持しつつ、**開発者（Tackman さん）が他人の Drive にアクセスできない設計**にする。

### 設計案 A（シンプル・個人用向け）
```
┌──────────────────────────────────────────────────┐
│ [1] 初回 OAuth 認証                              │
│     ユーザー → Google → アクセストークン +       │
│     リフレッシュトークン                          │
│     ↓                                           │
│ [2] ユーザーがリフレッシュトークンを             │
│     開発者の Worker に渡す                        │
│     ↓                                           │
│ [3] Worker がトークンを Secret に保存            │
│     ↓                                           │
│ [4] 以降、Worker は自分のトークンで API 呼び出し │
└──────────────────────────────────────────────────┘

⚠️ 問題：開発者が Worker の Secret を見れば、
         全ユーザーのトークンを取り出せる
```

### 設計案 B（プライバシー重視・将来マルチユーザー対応向け）
```
┌──────────────────────────────────────────────────┐
│ [1] 初回 OAuth 認証                              │
│     ユーザー → Google → アクセストークン +       │
│     リフレッシュトークン                          │
│     ↓                                           │
│ [2] リフレッシュトークンは                       │
│     ユーザーのブラウザ（localStorage）に保存     │
│     Worker には渡さない                           │
│     ↓                                           │
│ [3] アプリ（index.html）が API を呼ぶ時：          │
│     ・ブラウザがアクセストークンを取得           │
│     ・アクセストークンだけ Worker に渡す          │
│     ・Worker はアクセストークンで Google API 呼び │
│     ↓                                           │
│ [4] アクセストークン失効時：                      │
│     ・ブラウザがリフレッシュトークンで再発行      │
│     ・Worker は再発行を知らない                  │
└──────────────────────────────────────────────────┘

✅ メリット：開発者が他人のトークンを取り出せない
             （Worker はアクセストークンだけ扱う）
```

### 比較

| 観点 | 設計案 A（現状） | 設計案 B（推奨） |
|---|---|---|
| プライバシー | ❌ 開発者が全データを読める | ✅ 開発者は読めない |
| 実装複雑度 | ✅ シンプル | ⚠️ やや複雑 |
| ブラウザ変更時の UX | ✅ そのまま使える | ❌ 再 OAuth 認証が必要 |
| 個人用 | ✅ 問題なし | ✅ 問題なし |
| マルチユーザー対応 | ❌ 開発者に権限集中 | ✅ 各ユーザーが自分のデータだけ管理 |

## 6. なぜ開発者が他人の Drive にアクセスできないのか（設計案 B）

OAuth の仕組み上、**リフレッシュトークンを持つ人**が、**そのユーザーのデータ**にアクセスできる。

### 設計案 B の場合

```
┌──────────────────────────────────────────────────┐
│                                                    │
│  ユーザー A のブラウザ（A の localStorage）        │
│  ┌────────────────────────────┐                  │
│  │ リフレッシュトークン A       │ ← A だけが保持   │
│  └────────────────────────────┘                  │
│           │                                        │
│           │ アクセストークン取得（1時間ごと）      │
│           ▼                                        │
│  ┌────────────────────────────┐                  │
│  │ アクセストークン A          │                  │
│  └────────────────────────────┘                  │
│           │                                        │
│           ▼                                        │
│  ┌────────────────────────────┐                  │
│  │ Cloudflare Worker           │                  │
│  │ （A のアクセストークンで     │                  │
│  │  Google API を呼ぶだけ）     │                  │
│  │                              │                  │
│  │ ⚠️ リフレッシュトークンは    │                  │
│  │    持たない！                │                  │
│  └────────────────────────────┘                  │
│           │                                        │
│           ▼                                        │
│  ┌────────────────────────────┐                  │
│  │ Google Drive API             │                  │
│  │ （A のアクセストークンを検証 │                  │
│  │  A の Drive だけ返す）       │                  │
│  └────────────────────────────┘                  │
│                                                    │
└──────────────────────────────────────────────────┘
```

**Worker がリフレッシュトークンを持たない**ので、開発者が Worker のログや Secret を見ても、ユーザーのリフレッシュトークンは取り出せない。

ユーザー B のリフレッシュトークンも同じように **B のブラウザにだけ保存**されている。だから開発者が他人のデータを読む経路がない。

## 7. まとめ：なぜ「各自の Drive + 設計案 B」が安全なのか

| 脅威シナリオ | 設計案 A | 設計案 B |
|---|---|---|
| 開発者が他人のデータを読む | ⚠️ 可能（Worker Secret を見れば） | ✅ **不可能**（リフレッシュトークンが Worker にない） |
| 開発者が API キーで Anthropic にアクセス | ⚠️ 可能（Worker Secret に集約） | ✅ 可能（変わらず。Anthropic API キーだけ） |
| 他人が私の Drive を読む | ✅ 不可能（OAuth スコープが `drive.file` のみ） | ✅ 不可能（同じく） |
| ブラウザを変える | ✅ そのまま | ❌ 再 OAuth 認証が必要（個人用なら許容範囲） |
| デバイス変更 | ✅ Drive にデータはある | ✅ Drive にデータはある（再 OAuth 認証が必要） |
| ユーザーがログアウト | ✅ トークン削除 | ✅ トークン削除 |

**設計案 B は、わずかな UX 複雑度（ブラウザ変更時の再認証）と引き換えに、開発の透明性を大きく高められる**。個人用でも採用する価値あり。

## 8. 実装の要点

### リフレッシュトークンのブラウザ保存

```javascript
// 初回 OAuth 認証完了後
localStorage.setItem("second-brain-youtube-refresh-token", refreshToken);

// アクセストークン取得時
const refreshToken = localStorage.getItem("second-brain-youtube-refresh-token");
const accessToken = await refreshAccessToken(refreshToken, env.YOUTUBE_CLIENT_ID, env.YOUTUBE_CLIENT_SECRET);
// accessToken だけ Worker に渡す
```

### Worker 側の変更

Worker はリフレッシュトークンを受け取らない。**アクセストークンだけ**受け取って API を呼ぶ：

```javascript
// Worker の /youtube-transcript エンドポイント
async function handleYouTubeTranscript(request, env) {
  const { url, accessToken } = await request.json(); // ← accessToken だけ
  
  const videoId = extractYouTubeId(url);
  
  // YouTube captions API を呼ぶ
  const captionsRes = await fetch(
    `https://www.googleapis.com/youtube/v3/captions?part=snippet&videoId=${videoId}`,
    { headers: { Authorization: `Bearer ${accessToken}` } }
  );
  
  // ...
}
```

## 9. 用語集（簡潔な補足）

- **OAuth**：アプリに限定的なアクセス権を与える認証プロトコル
- **アクセストークン**：API 呼び出しに使う短期のトークン（1時間程度）
- **リフレッシュトークン**：アクセストークンを再発行するための長期のトークン
- **localStorage**：ブラウザ内のデータ保存領域（5〜10 MB）
- **スコープ**：アプリに許可する操作の範囲（`drive.file`、`youtube.force-ssl` など）
- **API キー**：Google Cloud で発行する鍵。OAuth とは別の認証方式（`captions.list` など一部 API で使える）
- **Worker**：Cloudflare のサーバーサイド JavaScript 実行環境
- **Secret**：Cloudflare Workers の暗号化環境変数。ログにも表示されない

## 10. 修正履歴

### 2026-07-26：OAuth Client のスコープ設定について誤った情報を提供

Claude Code（私）が OAuth のスコープ管理について複数回誤った情報を提供しました。Tackman さんの観察と検証により訂正。

#### 誤った情報（撤回済み）

1. **「OAuth Client 設定にスコープ設定がある」** ← 誤り
   - 実際：OAuth Client（APIとサービス → 認証情報）には名前、Client ID、Authorized JavaScript origins、Authorized redirect URIs のみ。**スコープ設定はない**。
   - 確認方法：OAuth Client のウェブアプリケーションの詳細情報画面に「名前」「承認済みの JavaScript 生成元」「承認済みのリダイレクト URI」のみが表示される。

2. **「OAuth 同意画面から削除すれば OK」** ← 単純化しすぎ
   - 実際：OAuth 同意画面の「データアクセス」セクションからスコープを削除する必要があるが、Google の OAuth サーバーに反映されるまでに時間がかかることがある。

3. **「時間を置けば反映される」** ← 具体的な時間が不明
   - 実際：数分〜数十分で反映されるが、稀に数時間かかることもある（2026-07-26 時点で未確認）。

#### 正しい OAuth のスコープ管理

- **OAuth Client 自体**にはスコープ設定はない（ユーザー観察で確定）
- **OAuth フローのスコープ**はコード（`initTokenClient` の `scope`）で決定
- **プロジェクト全体のスコープ**は OAuth 同意画面の「データアクセス」セクションで管理
- **OAuth Client ごとに個別のスコープ設定はできない**（プロジェクト単位）

#### ユーザー観察により得られた正確な情報（Tackman さん）

- OAuth Client のウェブアプリケーション詳細画面に「名前」「承認済みの JavaScript 生成元」「承認済みのリダイレクト URI」しか表示されない
- 別のプロジェクト（Drive / YouTube 用）のデータアクセスにもなんのスコープも設定されていなかった
- OAuth 同意画面から `youtube.force-ssl` を削除したのに、ブラウザキャッシュクリア後も YouTube スコープエラーが解消されない

#### 今後の調査時の注意事項

Claude Code への指示（Tackman さん）：「今後、1度誤った認識で私に情報を伝えていることが分かったら、必ずそのシステムの設定方法などを調査して、正しい情報を伝えるようにしてください」

- OAuth のスコープ管理のように、UI のどこで何が設定できるかは**実装で確認しないと正確には分からない**
- 推測ではなく、実際にコンソール画面・コード・公式ドキュメントを確認する
- 1 度誤ったら「もう間違えない」と意識する

### 2026-07-26：OAuth 同意画面のキャッシュ問題

OAuth 同意画面の「データアクセス」セクションから `youtube.force-ssl` を削除しても、ブラウザキャッシュクリア後も OAuth フローで YouTube スコープエラーが出る場合、**Google の OAuth サーバー側のキャッシュ**が原因の可能性。

**推奨対応**：時間を置く（数時間〜翌日まで）。OAuth サーバー側のキャッシュ更新を待つ。

**代替対応**：時間が解決しない場合は、Google Cloud プロジェクトを新規作成して OAuth Client をゼロから作る（最終手段）。
